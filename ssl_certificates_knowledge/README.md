# Let's Encrypt Wildcard Certificates with Certbot, AWS Route 53, and Apache on Ubuntu

> A practical knowledge-base guide for obtaining, validating, using, and
> automatically renewing a Let's Encrypt certificate with Certbot's
> Route 53 DNS plugin.

## Architecture at a Glance

This guide uses the **DNS-01 challenge**. Certbot proves control of a
domain by temporarily creating a DNS TXT record in the domain's
authoritative Route 53 hosted zone.

``` text
Ubuntu Server
   |
   | Certbot + dns-route53 plugin
   | AWS credentials / IAM permissions
   v
AWS Route 53
   |
   | temporary TXT record:
   | _acme-challenge.example.com
   v
Public DNS <---------------- Let's Encrypt ACME service
                                  |
                                  | validates DNS control
                                  v
                         Certificate issued
                                  |
                                  v
                    /etc/letsencrypt/live/...
                                  |
                                  v
                           Apache HTTPS :443
                                  |
                                  v
                         Application/backend
```

**Important:** DNS resolution and certificate trust are different
things. An `A` record such as `jenkins.example.com -> 192.168.1.50`
tells a client **where to connect**. It does not make the certificate
valid. Let's Encrypt issues the certificate after independently
validating control of the domain through DNS.

This workflow requires outbound Internet connectivity from the Certbot
host to the Let's Encrypt ACME service, and Let's Encrypt must be able
to query the domain's **public DNS**. It is therefore not directly
suitable for a fully isolated environment with no Internet access.

## 1. Prerequisites

Before requesting a certificate, make sure all of the following are
true:

-   You control the domain for which the certificate will be requested.
-   The domain's authoritative DNS is hosted in **AWS Route 53**.
-   The Ubuntu system has outbound Internet access.
-   AWS CLI credentials are already configured on the Ubuntu system.
-   Those AWS credentials have permission to view the appropriate hosted
    zone and create/delete DNS records in it.
-   The system has `sudo` or root access.
-   The system clock is reasonably accurate.
-   For a wildcard certificate such as `*.example.com`, use a DNS
    challenge. DNS-01 is what allows wildcard validation.
-   The private key generated by Certbot must be protected. Do not copy
    it into Git or other public storage.

In certificate-authority terminology, "owning" the domain really means
being able to **prove control** of it. With DNS-01, control is
demonstrated by publishing a special TXT record under the domain when
Let's Encrypt requests it.

## 2. Install Certbot Using Snap

Ubuntu normally includes `snapd`. Verify it first:

``` bash
snap --version
```

If Snap is not installed:

``` bash
sudo apt update
sudo apt install snapd
```

If an older Certbot package was previously installed through APT, avoid
having two competing Certbot installations:

``` bash
which certbot
dpkg -l | grep certbot
```

If appropriate for a new/clean installation, remove the old APT Certbot
package before installing the Snap version.

Install Certbot:

``` bash
sudo snap install --classic certbot
```

Make the command available through the normal command path if needed:

``` bash
sudo ln -s /snap/bin/certbot /usr/local/bin/certbot
```

If the link already exists, do not recreate it.

Verify:

``` bash
which certbot
certbot --version
snap list certbot
```

A Snap installation normally resolves to `/snap/bin/certbot`.

------------------------------------------------------------------------

## 3. Install the Route 53 DNS Plugin

Allow Certbot's externally installed DNS plugin to run with the required
containment level:

``` bash
sudo snap set certbot trust-plugin-with-root=ok
```

Install the Route 53 plugin:

``` bash
sudo snap install certbot-dns-route53
```

Verify that Certbot sees it:

``` bash
sudo certbot plugins
```

Look for a plugin named similar to:

``` text
dns-route53
```

## 4. Verify AWS Identity and Route 53 Access

This guide assumes AWS CLI credentials are already configured.

### 4.1 Verify which AWS identity is being used

``` bash
aws sts get-caller-identity
```

This confirms that the credentials work and shows the AWS account and
IAM principal currently being used.

### 4.2 Verify Route 53 hosted-zone visibility

``` bash
aws route53 list-hosted-zones-by-name \
  --dns-name example.com \
  --max-items 1
```

Confirm that the expected hosted zone is returned.

You can also list the records in a known hosted zone:

``` bash
aws route53 list-resource-record-sets \
  --hosted-zone-id YOUR_HOSTED_ZONE_ID \
  --max-items 10
```

### 4.3 Required Route 53 permissions

The Certbot Route 53 plugin needs permissions including:

``` text
route53:ListHostedZones
route53:ListHostedZonesByName
route53:GetChange
route53:ChangeResourceRecordSets
```

A least-privilege policy should restrict `ChangeResourceRecordSets` to
the hosted zone Certbot actually needs to modify.

Example:

``` json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "route53:ListHostedZones",
        "route53:ListHostedZonesByName",
        "route53:GetChange"
      ],
      "Resource": "*"
    },
    {
      "Effect": "Allow",
      "Action": "route53:ChangeResourceRecordSets",
      "Resource": "arn:aws:route53:::hostedzone/YOUR_HOSTED_ZONE_ID"
    }
  ]
}
```

### Important security note

Avoid testing write permission by creating arbitrary production DNS
records unless necessary. The safest end-to-end test is Certbot's own
staging/dry-run process, which creates the ACME challenge record it
actually needs and cleans it up.

Also prefer an IAM role or tightly scoped credentials where possible.
Never commit `aws_access_key_id`, `aws_secret_access_key`, or Certbot
private keys to Git.

## 5. Request a Let's Encrypt Wildcard Certificate

Example for `example.com` and all one-level subdomains:

``` bash
sudo certbot certonly \
  --dns-route53 \
  -d example.com \
  -d '*.example.com' \
  --agree-tos \
  --email admin@example.com \
  --non-interactive
```

Replace the domain and email address with your own values.

### What happens behind the scenes?

1.  Certbot connects to the Let's Encrypt ACME service over the
    Internet.

2.  Let's Encrypt supplies a DNS-01 challenge.

3.  The `dns-route53` plugin authenticates to AWS using available AWS
    credentials.

4.  Certbot creates a temporary record similar to:

    ``` text
    _acme-challenge.example.com  TXT  "<challenge-token>"
    ```

5.  Let's Encrypt independently queries public DNS for that TXT record.

6.  Finding the expected token proves that the requester controls DNS
    for the domain.

7.  Let's Encrypt issues a signed certificate.

8.  Certbot stores the certificate and private key locally.

9.  The temporary challenge record is normally removed after validation.

A wildcard certificate for:

``` text
*.example.com
```

covers names such as:

``` text
jenkins.example.com
grafana.example.com
argocd.example.com
```

It does **not** cover deeper names such as `foo.bar.example.com`, and it
does not make a certificate valid for a raw private IP address such as
`192.168.1.50`.

## 6. Inspect and Validate the Certificate

List Certbot-managed certificates:

``` bash
sudo certbot certificates
```

Typical paths are:

``` text
/etc/letsencrypt/live/example.com/fullchain.pem
/etc/letsencrypt/live/example.com/privkey.pem
```

Inspect validity dates:

``` bash
sudo openssl x509 \
  -in /etc/letsencrypt/live/example.com/fullchain.pem \
  -noout -dates
```

Inspect the subject, issuer, dates, and Subject Alternative Names:

``` bash
sudo openssl x509 \
  -in /etc/letsencrypt/live/example.com/fullchain.pem \
  -noout \
  -subject \
  -issuer \
  -dates \
  -ext subjectAltName
```

`notBefore` is the start of the certificate's validity period;
`notAfter` is its expiration time.

For a stronger identity check:

``` bash
sudo openssl x509 \
  -in /etc/letsencrypt/live/example.com/fullchain.pem \
  -noout -serial -dates -fingerprint -sha256
```

## 7. Configure Apache to Use the Certificate

Assume an application such as Jenkins is running locally on:

``` text
http://127.0.0.1:8080
```

The desired user-facing URL is:

``` text
https://jenkins.example.com
```

Enable the Apache modules needed for HTTPS and reverse proxying:

``` bash
sudo a2enmod ssl proxy proxy_http headers
```

Create a virtual host:

``` bash
sudo nano /etc/apache2/sites-available/jenkins.example.com.conf
```

Example:

``` apache
<VirtualHost *:80>
    ServerName jenkins.example.com
    Redirect permanent / https://jenkins.example.com/
</VirtualHost>

<VirtualHost *:443>
    ServerName jenkins.example.com

    SSLEngine on
    SSLCertificateFile /etc/letsencrypt/live/example.com/fullchain.pem
    SSLCertificateKeyFile /etc/letsencrypt/live/example.com/privkey.pem

    ProxyRequests Off
    ProxyPreserveHost On

    ProxyPass        / http://127.0.0.1:8080/
    ProxyPassReverse / http://127.0.0.1:8080/

    RequestHeader set X-Forwarded-Proto "https"
    RequestHeader set X-Forwarded-Port "443"

    ErrorLog ${APACHE_LOG_DIR}/jenkins-error.log
    CustomLog ${APACHE_LOG_DIR}/jenkins-access.log combined
</VirtualHost>
```

Enable the site and validate Apache:

``` bash
sudo a2ensite jenkins.example.com.conf
sudo apachectl configtest
sudo systemctl reload apache2
```

`configtest` should report:

``` text
Syntax OK
```

### DNS record for the application

Create the appropriate DNS record separately, for example:

``` text
jenkins.example.com  A  <server-IP>
```

Remember:

``` text
DNS       -> tells the browser WHERE to connect
Certificate -> tells the browser whether the HTTPS identity can be TRUSTED
```

For a private home-lab address, public Route 53 can technically return a
private RFC1918 IP, but only clients with network reachability to that
private IP can connect.

## 8. Verify the Certificate Apache Is Actually Serving

Do not assume that because the files on disk changed, Apache is already
serving them.

Inspect the certificate currently presented by Apache:

``` bash
echo | openssl s_client \
  -connect 127.0.0.1:443 \
  -servername jenkins.example.com 2>/dev/null \
  | openssl x509 -noout -serial -dates -fingerprint -sha256
```

Compare that with the certificate on disk:

``` bash
sudo openssl x509 \
  -in /etc/letsencrypt/live/example.com/fullchain.pem \
  -noout -serial -dates -fingerprint -sha256
```

If the serial number and SHA-256 fingerprint match, Apache is serving
the current certificate.

The `-servername` option is important because it supplies **SNI**,
allowing Apache to select the correct TLS virtual host.

## 9. Verify Automatic Certificate Renewal

Certbot's Snap installation normally creates a systemd renewal timer.

Check it:

``` bash
systemctl list-timers --all | grep -i certbot
```

A Snap installation may show:

``` text
snap.certbot.renew.timer
snap.certbot.renew.service
```

Inspect the timer:

``` bash
systemctl status snap.certbot.renew.timer
```

Inspect the service:

``` bash
systemctl cat snap.certbot.renew.service
```

Certbot periodically runs renewal checks. A scheduled check does **not**
mean a new certificate is issued every time. If the certificate is not
ready for renewal, Certbot simply leaves it alone.

You can inspect the saved renewal configuration:

``` bash
sudo grep -E 'authenticator|installer' \
  /etc/letsencrypt/renewal/example.com.conf
```

For this workflow, the authenticator should reflect Route 53.

Avoid casually editing files under `/etc/letsencrypt/renewal/`; Certbot
recommends using its commands to change renewal configuration.

## 10. Test Renewal Safely

Run:

``` bash
sudo certbot renew --dry-run
```

A successful result should end with a message indicating that all
simulated renewals succeeded.

`--dry-run` uses the Let's Encrypt staging environment and does not
replace the active production certificate.

This test validates much of the real renewal chain:

``` text
Certbot
  -> saved renewal configuration
  -> dns-route53 plugin
  -> AWS authentication
  -> Route 53 DNS update
  -> public DNS
  -> Let's Encrypt staging ACME service
  -> DNS-01 validation
  -> simulated certificate renewal
```

This is also why an Internet-restricted environment requires a different
PKI design: Certbot must reach the ACME service, and the public CA must
be able to validate the public DNS challenge.

------------------------------------------------------------------------

## 11. Make Sure Apache Loads Renewed Certificates

Certbot updates certificate files/symlinks under:

``` text
/etc/letsencrypt/live/example.com/
```

Apache needs to reload after a real renewal so that it starts serving
the new certificate.

### Option A: Explicit Certbot deploy hook --- recommended

Create:

``` bash
sudo nano /etc/letsencrypt/renewal-hooks/deploy/reload-apache.sh
```

Contents:

``` bash
#!/bin/bash
systemctl reload apache2
```

Make it executable:

``` bash
sudo chmod +x /etc/letsencrypt/renewal-hooks/deploy/reload-apache.sh
```

A deploy hook runs after a successful certificate deployment, directly
associating certificate renewal with the Apache reload.

Test the renewal plus deploy-hook path:

``` bash
sudo certbot renew --dry-run --run-deploy-hooks
```

### Option B: Apache may already be reloaded by another mechanism

On Ubuntu, Apache log rotation commonly includes a `postrotate` action
that reloads Apache.

Inspect:

``` bash
cat /etc/logrotate.d/apache2
```

You may see logic similar to:

``` text
invoke-rc.d apache2 reload
```

If log rotation is daily, Apache will eventually reread a newly renewed
certificate even without a Certbot deploy hook. However, an explicit
Certbot deploy hook is cleaner because the reload happens immediately
after successful renewal rather than depending on an unrelated scheduled
event.

Check Apache reload history:

``` bash
journalctl -u apache2 --since "7 days ago"
```

## 12. End-to-End Renewal Flow

``` text
snap.certbot.renew.timer
        |
        v
snap.certbot.renew.service
        |
        v
certbot renew
        |
        +---- certificate not due? ----> do nothing
        |
        +---- certificate due
                  |
                  v
          dns-route53 plugin
                  |
                  v
            AWS credentials
                  |
                  v
             Route 53
                  |
                  v
 _acme-challenge.example.com TXT
                  |
                  v
        PUBLIC INTERNET / DNS
                  |
                  v
       Let's Encrypt ACME service
                  |
                  v
        DNS control validated
                  |
                  v
       New certificate issued
                  |
                  v
 /etc/letsencrypt/live/example.com/
                  |
                  v
          Apache reload
                  |
                  v
     New certificate served
                  |
                  v
   https://jenkins.example.com
```

## 13. Troubleshooting Checklist

### Certbot cannot authenticate to AWS

``` bash
aws sts get-caller-identity
```

Then verify Route 53 access:

``` bash
aws route53 list-hosted-zones-by-name --dns-name example.com
```

### Certbot cannot create the challenge

Check IAM permissions, especially:

``` text
route53:ChangeResourceRecordSets
route53:GetChange
route53:ListHostedZones
```

### Route 53 challenge appears but validation fails

Check public DNS:

``` bash
dig TXT _acme-challenge.example.com
```

Remember that the challenge record may be temporary and disappear after
validation.

### Certificate exists but Apache does not serve it

Compare the on-disk and served fingerprints as shown earlier, then
reload Apache:

``` bash
sudo apachectl configtest
sudo systemctl reload apache2
```

### Check Certbot logs

``` bash
sudo less /var/log/letsencrypt/letsencrypt.log
```

For recent renewal-related messages:

``` bash
sudo grep -iE 'renew|success|failure|error' \
  /var/log/letsencrypt/letsencrypt.log | tail -50
```

## 14. Security Notes

-   Never commit AWS access keys or secret keys to Git.
-   Never commit `/etc/letsencrypt/live/*/privkey.pem`.
-   Use least-privilege IAM permissions for Route 53.
-   Prefer IAM roles or short-lived credentials where practical.
-   Keep the Certbot host and Snap packages patched.
-   Restrict direct access to backend applications when Apache is
    intended to be the secure entry point.
-   A wildcard certificate is convenient, but compromise of its private
    key affects every hostname using that certificate.
-   DNS-01 proves control of DNS; it does not prove legal ownership of a
    business or organization.
-   Publicly trusted Let's Encrypt issuance/renewal depends on
    Internet-accessible ACME infrastructure and public DNS. Fully
    isolated networks generally need an internal CA/private PKI or an
    internally reachable ACME service instead.

## Key Takeaway

The complete trust chain is:

``` text
AWS credentials
      |
      v
Permission to modify Route 53 DNS
      |
      v
DNS-01 proves control of the domain
      |
      v
Let's Encrypt signs a certificate
      |
      v
Apache presents that certificate
      |
      v
Browser verifies:
  - trusted CA chain
  - hostname match
  - validity period
  - cryptographic signature
      |
      v
Secure HTTPS connection
```

The application's ordinary DNS `A`/`AAAA`/`CNAME` record and the ACME
DNS-01 challenge serve different purposes: **DNS locates the service;
DNS-01 proves domain control for certificate issuance; TLS then provides
authenticated, encrypted communication.**
